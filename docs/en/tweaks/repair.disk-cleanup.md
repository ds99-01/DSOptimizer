# repair.disk-cleanup – Clean up the disk

## Verdict for 26H2
Port as `kind=action`, `risk=safe` ("Repairs" category, Stage 4b batch 2, a long repair with a progress window). A fixed set from spec 5.2, with the mechanism of each step chosen by measurement on 26H2 Home and Pro VMs (`docs/zrodla/2026-10-22-etap4b-2-pomiary.md` (in Polish), item 4): direct deletion in C# for files, a cmdlet for Delivery Optimization, DISM for the component store. **No `cleanmgr`** (measurements 4a and 4f: slower, deletes less, doesn't finish from session 0). The gain from Delivery Optimization on the VM is small (files being downloaded at that moment stay) – a large gain after finished downloads is **to be confirmed on hardware**.

## What it changes
C# handler `disk-cleanup` (`DiskCleanupHandler`), without a catalog script:
1. The `ServicingGuard` guard: a running `dism`, `sfc` or `cleanmgr` process = `Refused` "The previous servicing operation is still in progress – try again in a moment.", nothing starts. Then the free space of the system drive (`IDiskSpace`, `GetDiskFreeSpaceExW`).
2. Step 1 of 6 "System temporary files": `%SystemRoot%\Temp` – files with a `LastWriteTimeUtc` older than 24 h (`IRepairFileSystem.DeleteOldFiles`, Task 4): deletion through a handle (`FILE_FLAG_OPEN_REPARSE_POINT`, `share 0` – a file opened by anyone, even with `FILE_SHARE_DELETE`, stays as "in use"), the final path from the handle must be under the folder being cleaned, junctions and symbolic links are deleted as the link only (target untouched), a subfolder is also checked through a handle before entering it (replaced by a link = we don't enter), empty old subfolders disappear, the folder itself stays. Missing folder = skipped.
3. Step 2 of 6 "Account temporary files": `<profile>\AppData\Local\Temp` of the signed-in account, the same way. The profile comes from the `ProfileImagePath` value of the key `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList\<SID>` (`IRegistry`, environment variables expanded). Skipped with a note when `IUserContext.IsCertain = false` (it isn't known who is signed in – the program doesn't clean its own account instead), the SID has a wrong format, the value is missing or the path isn't a full local path (`X:\…`, no UNC and no `..`).
4. Step 3 of 6 "Delivery Optimization": the script `DiskCleanupScripts.DeliveryOptimization` through `IScriptRunner` (limit `timeoutSeconds`): `Delete-DeliveryOptimizationCache -Force`; command missing (helper `Test-DsoDeliveryOptimizationCmdlet`) = skipped; cmdlet error = step error with the stderr content. The result comes from a marker in the last line (`DSO:DO-WYKONANO` / `DSO:DO-BRAK-POLECENIA`), because the cmdlet writes to the host stream. No verification of the cache size – the only evidence is that the cmdlet didn't report an error, so the step line says "done – the command finished without an error (files being downloaded right now stay)", not "cleared". After the limit the script is interrupted (the scripts' Job Object; this isn't DISM/SFC/cleanmgr) and the step ends with an error – together with the DISM limit in step 5, the worst case is about 40 min of waiting.
5. Step 4 of 6 "Downloaded updates": no `%SystemRoot%\SoftwareDistribution\Download` = skipped without touching the services (fresh VM – measurement 4c). Otherwise reading `wuauserv` and `bits`, stopping the running ones in this order (`ServiceStopRestore` – logic extracted from the Windows Update reset without a change in behavior), `DeleteOldFiles(…\Download, DateTime.MaxValue)` (everything except files in use), restoring the services in reverse order with a reading of their state. A service didn't stop = step skipped, the services return to their previous state. A service didn't come back = step error and an entry in "Not restored".
6. Step 5 of 6 "Component store": `%SystemRoot%\System32\dism.exe /Online /Cleanup-Image /StartComponentCleanup` **without** `/ResetBase` through `IServicingToolRunner` (`CreateProcessW` with the full path, outside the Job Object, never killed, limit = `timeoutSeconds` = 1200 s), the percentage from the DISM bar goes to the progress window ("Step 5 of 6 · Next: Account thumbnails"). Code 0 = done, 3010 (`ERROR_SUCCESS_REBOOT_REQUIRED`) = done with a restart (**not measured**, as in `repair.system-files`), any other = error with the code and `%SystemRoot%\Logs\DISM\dism.log`. After the limit: "still running in the background after 20 min – the program stopped waiting, and DISM keeps working", overall result `NotConfirmed`. Success is judged by the exit code, **not** by the `Number of Reclaimable Packages` line in `/AnalyzeComponentStore` – it stays after a cleanup without `/ResetBase` (measurement 4d).
7. Step 6 of 6 "Account thumbnails": `thumbcache_*.db` files directly in `<profile>\AppData\Local\Microsoft\Windows\Explorer` (`IRepairFileSystem.DeleteFilesByName`, the same handle mechanism, no subfolders, no `iconcache_*`); locked ones are skipped and counted. Account condition as in step 2.
8. Free space after. Message: "Freed: <DiskSpaceText.Freed>." (MB or GB with one decimal place, rounded down; a drop in free space = "the freed space can't be reported honestly (other programs were writing to the disk)") and one line per step: "done (files: N, X; kept, newer than 24 h: …; kept, in use: …)", "skipped – <reason>", "error – <reason>".

Result: `Executed` when no step has an error and nothing was left running in the background; a step error = `Failed` with the list (the other steps run anyway, Ruling R20: an error also wins over a stop and the time limit); DISM after the limit or "Stop" between steps (the remaining steps "skipped – stopped.") = `NotConfirmed` (Ruling R10). Skips don't spoil the result (spec 2).

Doesn't touch: the Recycle Bin, the Downloads folder, restore points, memory dumps (`*.dmp`, `Minidump`), Windows.old (a separate item) – spec 5.2, test `NeverTouchesRecycleBinDownloadsDumps`.

## Defaults on a fresh 26H2
`SoftwareDistribution\Download` doesn't exist (step 4 skipped), the DO cache is empty without a network, thumbnails of the `dso` account: 15 files (2 × 1 MB + small ones) – reading 2026-10-22. The component store's "Cache and Temporary Data" of 481 MB (Home) / 404 MB (Pro) was read after earlier DISM runs in the same measurement, not on the checkpoint itself (see "Observed effect").

## Detection and undo
Not applicable: `kind=action` without detection and undo. The verification is the counters of the deletion through handles (deleted, new, in use, bytes), the DO script marker, the DISM exit code, the state of the services after the restore and the free space before/after. Deleted files can't be restored (they're temporary files and caches that Windows recreates).

## Risks and warnings
- `risk=safe`: only temporary files older than 24 h, caches and components replaced by newer ones; doesn't change settings.
- Time: usually under 1 min on a VM (DISM about 12 s); the wait limit for DISM is 20 min, after it DISM keeps working in the background.
- "Stop" works only between steps.
- During step 4 the `wuauserv` and `bits` services are stopped; an update being downloaded at that moment may download again (not measured).
- No `/ResetBase`, so none of the effect MS describes for `/ResetBase` ("All existing update packages can't be uninstalled after this command is completed"); according to MS, `/StartComponentCleanup` alone removes the previous versions of updated components right away, without the 30-day grace period of the Task Scheduler task.
- Known limitation (Task 4): between the handle check of a subfolder and its enumeration there's a narrow window; a swap in that window gives at most inflated counters, and deletions outside the tree are blocked by the final-path check of each element.

## VM test
Cases in `tests/vm/cases.psd1` (Task 7), `Flow='Execute'`, built-in catalog, no network:
- `repair-disk-cleanup` (`RunAs='dso'`, CLI from a Task Scheduler task of the `dso` account, so `IsCertain` = true and the process SID = the signed-in user);
- `repair-disk-cleanup-admin` (without `RunAs`, CLI as Administrator via PS Direct – the account steps apply to the signed-in `dso` by SID, not to the process account).

`Setup` of both: old (`LastWriteTime` −2 days) and fresh files and an old subfolder with an old file in `C:\Windows\Temp` and in the `%TEMP%` of the `dso` account; a junction `dso-dc-link` in the `%TEMP%` of the `dso` account pointing to `C:\dso\guard` with a guard file (−10 days), aged through `SetFileTime` on a handle with `FILE_FLAG_OPEN_REPARSE_POINT` (a fresh link would only be skipped as new); files in `SoftwareDistribution\Download` (with a subfolder); `thumbcache_dsotest.db` and `iconcache_dsotest.db` in the Explorer folder of the `dso` account; the state of `wuauserv`/`bits` saved. `Check` (independent reading in the VM): the old files and the old subfolder are gone, the fresh ones stayed, the junction is gone as a link, the guard file is untouched, no test files in `Download`, `thumbcache_dsotest.db` is gone, `iconcache_dsotest.db` stayed, the services that were running before are running, `dism.exe` isn't running. `Expect`: `Executed`, code 0, `RequiresReboot = $false`, a message with the line "Magazyn składników: wykonano (DISM /StartComponentCleanup, kod 0)." (Component store: done (DISM /StartComponentCleanup, code 0).). `CliTimeoutSeconds = 2700` (the DISM and DO script limits are 1200 s, plus a margin; the run takes under 1 min).

VM runs (Task 7, 2026-10-23, `tests/vm/Invoke-VmTests.ps1 -CasesPath <only these two cases>`, branch `etap4b-2`; reports outside git): **Passed** on Home and Pro in both runs (14 passed / 0 failed each). CLI time: `repair-disk-cleanup` (first, `dso`) 20–54 s (DISM 17 s), `repair-disk-cleanup-admin` (second, store already cleaned) 3–9 s. Message (Home and Pro): system temporary files 2–3 deleted and 1 new one kept, account files 3–5 deleted and 1 new one kept, DO "wykonano" (done), downloaded updates 2 files, component store code 0, thumbnails 1–12 deleted and 4 in use (held by `explorer.exe` of the `dso` account). The first line in all runs: "Zwolniono: nie da się uczciwie podać zwolnionego miejsca (inne programy zapisywały na dysku)." (Freed: the freed space can't be reported honestly (other programs were writing to the disk).) – in the program log (raw readings), the free space on C: dropped by 1–120 MB during the run (the VM right after starting from the checkpoint; the test files are a few KB each). Review Focus 1 holds on a real system: no made-up number.

## Observed effect
Method: measurement of the mechanisms (Task 2, `tests/vm/explore/Invoke-E4B2Exploration.ps1`): a prepared set of files, the free space on C: before and after each step, folder sizes, `/AnalyzeComponentStore` before and after, process samples.
- **Home** (`DSO-26H2-Home`, 26300.9457), 2026-10-22: temporary files deleted directly – the old ones deleted, a fresh one and one opened without sharing stay, the junction deleted as a link, the guard file in the target untouched (4a); `Delete-DeliveryOptimizationCache -Force` with a cache of 5.16 GB / 4 jobs: 0.3 s, DO folder −28.6 MB, jobs in progress stay (4b); `SoftwareDistribution\Download` 255 MB / 8 files deleted with `wuauserv` and `bits` stopped (4c); `StartComponentCleanup` code 0 in 12.1 s, +449 MB ("Cache and Temporary Data" 481 MB → 0), `Number of Reclaimable Packages: 2` stays (4d); 15 thumbnail files of `dso` deleted with `explorer.exe` running (4e).
- **Pro** (`DSO-26H2-Pro`, 26300.9457), 2026-10-22: the same; DO 5.43 GB / 7 jobs → folder −28.6 MB; `StartComponentCleanup` code 0 in 11.7 s, +367 MB (404 MB → 0).
- `cleanmgr` "Temporary Files" from PS Direct: deletes only the file from 10 days ago, doesn't finish in 20 min (4a, 4f) – it isn't the mechanism of this item.
- The handler itself (2026-10-23, Home and Pro, cases `repair-disk-cleanup` and `repair-disk-cleanup-admin`): `Executed`; an independent reading in the VM confirms the deleted old files, the untouched fresh files and guard file behind the junction, the empty `Download`, the deleted thumbnail and the restored services. On a clean checkpoint `StartComponentCleanup` didn't free any measurable space (the free space on C: dropped by 1–120 MB during the run). The 449/367 MB from Task 2 (4d) was measured in a run where `DISM /RestoreHealth` and `/ScanHealth` had run earlier – they probably created the "Cache and Temporary Data" (**not measured**). How much space it frees on a computer in use: **to be confirmed on hardware**.
- A large gain from Delivery Optimization after finished downloads: **to be confirmed on hardware** (on the VM, WU was downloading during the measurement).
